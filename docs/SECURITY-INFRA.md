# Bilim Arena — защита от перегрузки и атак

Документ описывает, что **реально** защищено, где это сделано и чем проверено,
а что зависит от внешних сервисов и пока не настроено. Дата: 21.10.2026.

Обозначения: ✅ сделано в коде и проверено тестом · ⚙️ настройка в панели провайдера
(в коде не видна — проверить вручную) · ⚠️ остаточный риск.

## 1. Инфраструктура (подтверждено кодом и конфигурацией)

| Часть | Где | Что делает | Своя серверная логика |
|---|---|---|---|
| Сайт | GitHub Pages, `akbaralievernis.github.io/bilim_arena` | статические HTML/JS/CSS, без сборки | нет |
| Облако | Supabase `udkxmgflbxetfzziftla` (`core/config.js`) | Auth (почта учителя, анонимный ученик), PostgREST API, Postgres с RLS | **да — Postgres** (RLS, функции, триггеры) |
| Сервер знакомства | Cloudflare Workers + Durable Object, `bilimarena-signal…workers.dev` (`signal/`) | обмен служебными сообщениями WebRTC (PeerJS-протокол) | **да — Worker** |
| Запасной сервер знакомства | общий `0.peerjs.com` | то же, если свой недоступен | чужой, без наших лимитов |
| Ретранслятор (TURN) | Metered.ca, статические логин/пароль в `core/config.js` | трафик WebRTC в строгих сетях | нет |
| Урок | браузер учителя (доска) ↔ телефоны напрямую (WebRTC) | ответы учеников идут на доску, минуя серверы | доска — единственный «сервер» комнаты |
| Гонка | отдельный сайт на Vercel (`RACE_URL`), своя база | вне этого репозитория | — |

Не используются: собственный сервер/VPS, свой домен (нет `CNAME`), Supabase Realtime-каналы
(в `core/cloud.js` нет `channel()`), Edge Functions, `postMessage` между окнами.
Сторонних скриптов нет: библиотеки лежат в `vendor/`, CSP `script-src 'self'`, облачная
библиотека подключается с проверкой целостности (SRI, `core/cloud.js`).

## 2. Ограничения платформ

- **GitHub Pages**: нет WAF, нет правил ограничения частоты, нельзя задать HTTP-заголовки
  (CSP только через `<meta>`, поэтому не работают `frame-ancestors`, `X-Frame-Options` —
  страницы можно встроить во фрейм). От флуда защищает только CDN GitHub (Fastly) по
  своим правилам; мягкий лимит трафика — 100 ГБ/мес. Сайт статический: флуд не может
  «положить» базу через сайт, он бьёт по CDN GitHub.
- **Supabase (бесплатный тариф)**: API открыт всему интернету по публичному ключу — это
  нормально, защита держится на RLS и на лимитах в базе (раздел 3). Ограничения по IP есть
  только у Auth (⚙️ раздел 4). Своего WAF перед PostgREST нет.
- **Cloudflare Workers (бесплатно)**: 100 000 запросов в сутки. Автоматическая DDoS-защита
  Cloudflare работает и для `workers.dev`, но **правила WAF и Rate Limiting Rules доступны
  только для своего домена** (zone). Если квоту выбьют флудом, сайт сам переходит на
  общий PeerJS (`core/realtime.js`) — урок продолжается.
- **Доска и телефоны**: доверенного сервера между ними нет. Доска сама проверяет каждое
  сообщение (это и есть доверенная сторона комнаты), но не видит IP и не может отличить
  ученика от постороннего, знающего код.

## 4. Что настраивается в панелях (в коде не видно — ⚙️ проверить)

Ниже — значения **по умолчанию по документации провайдеров**. Фактические настройки проекта
из репозитория не видны; их нужно открыть и сверить.

**Supabase → Authentication → Rate Limits**
- Анонимные входы: по умолчанию 30 в час с одного IP. ⚠️ Класс из 40 учеников за одним
  школьным NAT может упереться в этот предел при первом входе в облако. Рекомендация:
  поднять до 200–300 в час и включить CAPTCHA для анонимного входа, если начнётся злоупотребление.
- Вход и регистрация (почта/пароль): лимит на IP — не снижать.
- Письма: на встроенной почте Supabase около 2 писем в час на весь проект — для реальной
  работы подключить свой SMTP.
- **Authentication → Attack Protection**: включить CAPTCHA (Cloudflare Turnstile) для
  регистрации учителя; для анонимного входа — только при атаке (требует правки `core/cloud.js`,
  передача `captchaToken`). Включить «Leaked password protection» (на платных тарифах).
- **Email**: включённое подтверждение почты скрывает, существует ли аккаунт (ответ на
  регистрацию одинаковый) — проверить, что включено.

**Supabase → Database**
- `statement_timeout` по умолчанию: `anon` 3 с, `authenticated` 8 с. Проверка:
  `select rolname, rolconfig from pg_roles where rolname in ('anon','authenticated');`
  Не менять без проверки (синхронизация больших вопросов с картинками).
- **API → Max rows**: по умолчанию 1000 строк на ответ — оставить.
- **Advisors → Security / Performance**: после миграции не должно быть предупреждений о
  RLS и `search_path`.

**Metered (TURN)**
- ⚠️ Логин и пароль статические и лежат в коде — любой может расходовать квоту 500 МБ/мес.
  Включить оповещение о расходе; при утечке — пересоздать учётные данные (раздел 6).

**Cloudflare (сервер знакомства)**
- `ALLOWED_ORIGINS` в `signal/wrangler.toml` — только сайт и localhost.
- Оповещения: Workers → Metrics, лимит 100 000 запросов/сутки.

## 5. Мониторинг

Где смотреть (без записи паролей, токенов и имён учеников):

| Что | Где |
|---|---|
| Ошибки сайта у пользователей | Supabase → Table Editor → `client_errors` |
| Всплески запросов, ответы 4xx/5xx, медленные запросы | Supabase → Reports (API, Database), Logs → API / Postgres |
| Ошибки входа, наплыв анонимных аккаунтов | Supabase → Logs → Auth; Authentication → Users (фильтр Anonymous) |
| Отказы RLS (403/42501), лимиты (429), размер (413) | Supabase → Logs → API, фильтр по статусу |
| Кто упирается в лимиты | SQL ниже |
| Сервер знакомства: запросы, ошибки, процессор | Cloudflare → Workers → bilimarena-signal → Metrics / Logs |
| Расход TURN | Metered → TURN Server → Usage |
| Сбои связи на уроке | `client_errors` (сообщения `realtime`), доска показывает «сервер знакомства» |

Полезные запросы (SQL Editor, роль владельца):

```sql
-- Кто чаще всех упирается в лимиты за последний час
select user_id, bucket, sum(hits) as hits, max(window_start) as last
from ba_private.rate_counters where window_start > now() - interval '1 hour'
group by 1, 2 order by hits desc limit 20;

-- Наплыв анонимных аккаунтов по часам
select date_trunc('hour', created_at) as hour, count(*) from auth.users
where is_anonymous and created_at > now() - interval '2 days' group by 1 order by 1 desc;

-- Самые большие записи (кто занимает место)
select user_id, key, pg_column_size(value) as bytes from public.user_data order by bytes desc limit 20;

-- Всплеск ошибок сайта
select date_trunc('minute', created_at) m, count(*) from public.client_errors
where created_at > now() - interval '1 hour' group by 1 order by 1 desc;
```

Объём данных мониторинга ограничен: счётчики лимитов хранятся сутки, журнал ошибок —
30 дней и не больше 300 записей за 10 минут.

## 6. Инструкция реагирования

1. **Распознать.** Признаки: в Supabase Reports резкий рост запросов или ответов 429/5xx;
   много новых анонимных аккаунтов; `client_errors` заполняется одинаковыми ошибками;
   учителя пишут, что телефоны не подключаются; Metered/Cloudflare сообщают о расходе квоты.
2. **Где смотреть.** Таблица в разделе 5. Запишите время начала, затронутую часть
   (база, вход, сервер знакомства, TURN) и примеры запросов.
3. **Временно ограничить.**
   - Перебор кодов / наплыв аккаунтов: Supabase → Auth → Rate Limits — снизить лимит
     анонимных входов; включить CAPTCHA; в крайнем случае отключить анонимный вход
     (уроки на доске работают без облака).
   - Злоупотребляет один пользователь: найти его в запросе «кто упирается в лимиты»,
     удалить аккаунт (Authentication → Users) — его данные удалятся каскадом.
   - Флуд записи в таблицу: уменьшить предел в триггере `ba_rate` этой таблицы
     (`create trigger … ba_rate_guard('<N>', '<окно>')`) через SQL Editor.
   - Сервер знакомства: уменьшить `IP_LIMITS` или временно сузить `ALLOWED_ORIGINS`, `npm run deploy`;
     если Worker недоступен, сайт сам уходит на общий PeerJS.
   - TURN: сменить учётные данные в Metered и в `core/config.js` (п. 6).
4. **Сохранить уроки.** Доска и телефоны работают без Supabase: облако нужно только для
   аккаунтов, заданий и синхронизации. При проблемах с облаком учитель ведёт урок как обычно;
   данные остаются на устройствах и синхронизируются позже. При отказе своего сервера
   знакомства работает общий PeerJS.
5. **Проверить восстановление.** Supabase Reports — частота запросов и ошибки вернулись к
   обычным; тестовый вход ученика по коду класса; урок на доске с телефоном (`?signal=own`);
   `select * from ba_private.rate_counters` — нет новых всплесков.
6. **Сменить скомпрометированные секреты.**
   - Ключ `service_role` / `sb_secret_…` (в код не попадает; если утёк): Supabase → Settings →
     API Keys → создать новый, удалить старый.
   - Публичный ключ (`sb_publishable_…`) секретом не является; при массовом злоупотреблении
     можно выпустить новый и заменить в `core/config.js`.
   - TURN: Metered → удалить учётные данные, создать новые, заменить в `core/config.js`, опубликовать.
   - Пароли учителей: Supabase → Authentication → Users → сбросить; при утечке базы — выход
     из всех сессий (Settings → JWT → rotate).
7. **Зафиксировать инцидент.** В `docs/` (или трекере): время начала и конца, что заметили,
   затронутые части и пользователи (без персональных данных учеников), принятые меры,
   изменённые настройки, сменённые секреты, что сделать, чтобы не повторилось.

## 8. Остаточные риски

- ⚠️ **Распределённый флуд** (много IP) на Supabase API: в базе он упирается в лимиты на
  пользователя, но запросы всё равно доходят до Supabase и расходуют его ресурсы. Защита —
  только инфраструктурная (раздел 9).
- ⚠️ **Массовые анонимные аккаунты** с разных IP: каждый получает свои лимиты. Ограничивают
  только лимиты Auth и CAPTCHA (⚙️).
- ⚠️ **Комната урока**: посторонний, узнавший 4-значный код (например, с фото доски), может
  войти и занять места поддельными именами. Нет кнопки «закрыть вход» и «удалить игрока».
- ⚠️ **Общий PeerJS** (запасной) — без наших лимитов, код комнаты там перебирается свободнее.
- ⚠️ **TURN** — статические учётные данные в коде.
- ⚠️ **Оценки** считаются в браузере ученика: результат в `submissions` можно подделать
  через API (размер и частота ограничены, достоверность — нет).
- ⚠️ **Фреймы**: GitHub Pages не позволяет запретить встраивание страниц (clickjacking).
- ⚠️ Счётчики Worker живут в памяти и сбрасываются, когда объект засыпает.

## 9. План перехода к минимальной доверенной инфраструктуре

Интерфейс сайта и адреса страниц не меняются. По шагам, от дешёвого к дорогому:

1. **Свой домен через Cloudflare** (≈ 10 $/год, тариф Free). Сайт — Cloudflare Pages
   (или GitHub Pages за прокси Cloudflare), сервер знакомства — `signal.<домен>`.
   Даёт: WAF и Rate Limiting Rules (1 правило бесплатно, например «≤ 100 запросов/10 с на IP
   к `/peerjs` и `/…/id`»), Bot Fight Mode, HTTP-заголовки через `_headers`
   (`Content-Security-Policy` с `frame-ancestors 'none'`, HSTS, `X-Content-Type-Options`).
   Изменения в коде: адреса в `core/config.js`, CSP, `ALLOWED_ORIGINS`.
2. **Временные учётные данные TURN через Worker.** Ключ Metered хранится как секрет Worker
   (`wrangler secret put`), сайт получает пароль на 1–2 часа через `GET /turn`
   (Origin + лимит по IP). В коде: `TURN.credentialsUrl` указывает на Worker вместо статического списка.
3. **CAPTCHA (Turnstile) для регистрации учителя**, для анонимного входа — по необходимости.
4. **Закрытие комнаты и удаление игрока на доске** — проверка полномочий в самой комнате
   (учитель «закрывает вход» после начала урока).
5. Если понадобится серверная проверка результатов — Supabase Edge Function, считающая
   оценку по ответам на стороне сервера (большое изменение, отдельный этап).
